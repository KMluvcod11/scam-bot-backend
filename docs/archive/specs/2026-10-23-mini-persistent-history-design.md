# Mini App: ประวัติจริงและดูเคสได้ตลอด — Design

วันที่: 2026-10-23 · สถานะ: รอผู้ใช้ทบทวน · โปรเจกต์: scam-bot-backend + Scam-bot-frontend

## 1. เป้าหมาย

ผู้ใช้เปิด Mini App แล้วเห็นประวัติการตรวจของตัวเองจากแชตส่วนตัวกับบอต เปิดดูรายละเอียดเคสเก่าได้ตลอด
(ไม่หมดอายุ 15 นาที และไม่หายเมื่อบอตรีสตาร์ต) และลบประวัติของตัวเองได้

### เกณฑ์สำเร็จ

1. ส่งข้อความวันนี้ วันถัดไปยังเห็นเคสในหน้าประวัติและเปิดรายละเอียดได้
2. รีสตาร์ตบอตแล้ว ประวัติและลิงก์ "ดูรายละเอียด" บนการ์ดเดิมยังเปิดได้
3. กด "ลบประวัติทั้งหมด" แล้วแถวของผู้ใช้ถูกลบจริงจาก Supabase และหน้าประวัติว่าง
4. ผู้ใช้เห็นเฉพาะเคสของตัวเอง เคสของคนอื่นตอบ 404 เหมือนเคสที่ไม่มีอยู่

### สิ่งที่ผู้ใช้เลือก

| เรื่อง | ตัวเลือก |
|---|---|
| แหล่งข้อความในประวัติ | เฉพาะแชตส่วนตัวกับบอต (`source_type = 'user'`) |
| อายุการเก็บ | เก็บตลอด มีปุ่มลบในหน้าบัญชี |
| การลบ | ลบจริงออกจากฐานข้อมูล |
| แนวทาง | อ่านจาก `detection_logs` โดยตรง (ไม่สร้างตารางใหม่) |

### นอกขอบเขต (YAGNI)

- การแบ่งหน้า (pagination): แสดง 50 รายการล่าสุดเท่านั้น
- ลบทีละรายการ: มีเฉพาะ "ลบทั้งหมดของฉัน"
- ข้อความในกลุ่มหรือห้อง
- เปลี่ยน schema หรือ RLS ของ Supabase

## 2. ข้อมูลและโครงสร้าง

### แหล่งข้อมูลเดียว: `public.detection_logs`

ตารางมีอยู่แล้ว (`supabase/dashboard_schema.sql`) และ `save_detection()` บันทึกทุกผลตรวจแชตส่วนตัวอยู่แล้ว
คอลัมน์ที่ใช้: `id uuid`, `line_event_id`, `source_type`, `sender_user_id`, `message_text`,
`detection_status`, `reason`, `received_at`

ไม่ต้องแก้ schema เพราะ:
- `id` เป็น uuid สุ่ม เดาไม่ได้ บอตส่งค่า `id` เองตอนบันทึกได้ จึงใช้เป็นรหัสเคสได้เลย
- บอตใช้ `SUPABASE_HISTORY_KEY` (secret key) ที่ข้าม RLS จึงอ่านและลบได้โดยไม่แก้ policy
- `warningPoints`, `nextSteps`, `lessonId` สร้างใหม่ได้จากข้อความและสถานะด้วย `build_case_detail()` โดยไม่เรียก AI

### รหัสเคส

- บอตสร้าง `case_id = uuid4()` ก่อนตอบ ใช้ทั้งในลิงก์บนการ์ดและเป็น `id` ของแถว
- ใน URL ใช้รูปแบบ 32 ตัวอักษรฐานสิบหกไม่มีขีด (`uuid.hex`) ตรงกับที่หน้าเว็บตรวจรูปแบบอยู่แล้ว
- ฝั่ง API แปลงกลับเป็น uuid ก่อนค้นหา รหัสผิดรูปแบบตอบ 404 โดยไม่เรียก Supabase

### การไหลตอนผู้ใช้ส่งข้อความ (แชตส่วนตัว)

1. ตรวจเสร็จ → `open_result_case()` สร้าง `case_id` และการ์ด (ลิงก์ `?case=<hex>`)
2. ส่งการ์ดตอบผู้ใช้ (เหมือนปัจจุบัน)
3. `save_detection(event, result, ..., case_id=case_id)` บันทึกแถวด้วย `id = case_id`
   - ยังใช้ `upsert(on_conflict="line_event_id", ignore_duplicates=True)` LINE ส่ง event ซ้ำไม่เกิดแถวซ้ำ
4. รูปภาพ: `message_text = "[รูปภาพ] " + ข้อความ OCR` (เดิมเป็น `"[รูปภาพ]"`) ถ้า OCR ไม่ได้ข้อความ ใช้ `"[รูปภาพ]"` เหมือนเดิม

### การอ่าน

เลือกแถวที่ `sender_user_id = sub` (จาก `verify_line_owner()`), `source_type = 'user'`
และ `detection_status in ('risk_found', 'uncertain', 'no_risk_found')`

### การลบ

ลบทุกแถวที่ `sender_user_id = sub` และ `source_type = 'user'` ทุกสถานะ (รวมคำทักทายและ error)
ไม่แตะแถวของกลุ่มหรือห้อง

### `LessonStore` (RAM)

ยังคงไว้เฉพาะบทเรียนในแชตแบบ postback (`learn:<id>`) ซึ่งใช้เมื่อไม่ได้ตั้งค่า LIFF
Mini App ไม่อ่านจาก `LessonStore` อีก

### ผลกระทบ

- **Dashboard:** `dashboard_daily_stats` นับจาก `detection_logs` โดยตรง เมื่อผู้ใช้ลบ ตัวเลขย้อนหลังจะลดลง ต้องแจ้งผู้ดูแล Dashboard
- **เคสเก่า:** แถวที่บันทึกก่อนงานนี้เปิดได้ด้วย `id` เดิม แต่เคสรูปเก่าจะเห็นข้อความเพียง `[รูปภาพ]`
- **ลิงก์บนการ์ดเก่า** (สร้างจาก `LessonStore` ก่อนงานนี้) ใช้รหัสที่ไม่ตรงกับแถวใดในฐานข้อมูล จะตอบ 404
- **บันทึกล้มเหลว:** ถ้า `save_detection()` ล้มเหลว ลิงก์บนการ์ดจะเปิดไม่เจอ (404) หน้าเว็บแสดงข้อความว่าเปิดไม่ได้

## 3. Backend

### ไฟล์ใหม่ `mini_history.py`

อ่านและลบประวัติจาก Supabase อย่างเดียว ใช้ client จาก `detection_history._history_client()`

| ฟังก์ชัน | รับ | ทำ | คืน | ถ้าพัง |
|---|---|---|---|---|
| `list_cases(owner, limit=50)` | `sub`, จำนวน | select คอลัมน์ที่ต้องใช้ ตามเงื่อนไขการอ่าน เรียง `received_at desc` | `[{id, title, category, receivedAt, status}]` | ยก `HistoryUnavailable` |
| `get_case(case_hex, owner)` | รหัส 32 ตัว, `sub` | แปลงเป็น uuid → select แถวเดียวตามเงื่อนไขการอ่าน → `build_case_detail()` | รายละเอียดรูปแบบ `MiniCaseData` หรือ `None` | ยก `HistoryUnavailable` |
| `delete_all(owner)` | `sub` | delete ตามเงื่อนไขการลบ | จำนวนแถวที่ลบ | ยก `HistoryUnavailable` |

- `title` = 60 ตัวอักษรแรกของข้อความ (ช่องว่างรวมเป็นหนึ่ง) รายการไม่ส่งข้อความเต็ม
- `category` = `"message"` ทุกเคส (หน้าเว็บรับ `link`/`message`/`gift`)
- `HistoryUnavailable` ห่อ exception ของ Supabase โดยไม่เก็บข้อความดิบ

### `mini_api.py`

ทุก endpoint เรียก `verify_line_owner()` ก่อน และใช้ `PRIVATE_HEADERS` (`no-store`, `no-referrer`)

| Endpoint | คืน | Error |
|---|---|---|
| `GET /api/mini/history` | `{"cases": [...]}` | 401 token, 503 ระบบประวัติขัดข้อง |
| `GET /api/mini/cases/{id}` | รายละเอียดเคส (รูปแบบเดิม) | 401, 404 ไม่มีหรือไม่ใช่ของเรา, 503 |
| `DELETE /api/mini/history` | `{"deleted": n}` (เรียกซ้ำได้) | 401, 503 |

ข้อความ 503: "ระบบประวัติขัดข้อง กรุณาลองใหม่ภายหลัง" ไม่ส่ง exception ดิบ

`create_mini_router()` รับ object ที่มี 3 ฟังก์ชันข้างบน (ใน `main.py` ส่งโมดูล `mini_history`)
เพื่อให้เทสต์ใส่ของจำลองได้

### `detection_history.py`

`save_detection(event, result, *, warning_attempted, warning_sent, case_id=None, image_text=None)`:
- ถ้ามี `case_id` ใส่เป็น `id` ของแถว (ไม่มี = ให้ Supabase สร้างเหมือนเดิม เช่น ข้อความในกลุ่ม)
- รูปภาพ: ถ้ามี `image_text` บันทึก `"[รูปภาพ] " + image_text` ไม่มีใช้ `"[รูปภาพ]"`

### `main.py`

- `open_result_case()` สร้าง `case_id = uuid4()` ใช้ในการ์ด และคืนให้ผู้เรียกส่งต่อให้ `save_detection()`
- ยังเพิ่มบทเรียนลง `LessonStore` เฉพาะผล `risk_found` (สำหรับ postback) โดยใช้รหัสเดียวกัน
- CORS: เพิ่มเมธอด `DELETE` ถ้าตั้งค่าแบบคนละโดเมน (ตอนนี้ใช้ Vite proxy แบบโดเมนเดียว)

## 4. Frontend

### `services/miniApi.ts`

- `fetchMiniHistory(token, signal)` และ `deleteMiniHistory(token)` ใช้รูปแบบคำขอเดียวกับ `fetchMiniCase()`
  (header `Authorization`, `cache: 'no-store'`, `credentials: 'omit'`, `redirect: 'error'`, `referrerPolicy: 'no-referrer'`)
- ตรวจรูปแบบทุกรายการ รายการผิดรูปแบบถูกตัดทิ้ง ไม่ทำให้ทั้งหน้าพัง
- แปลงรหัสสถานะเป็นข้อความผู้ใช้เข้าใจ (401 / 503 / เครือข่ายล้ม) ไม่แสดงข้อความดิบจาก server
- `fetchMiniCase()` ได้ 404 ครั้งแรก รอ 1.5 วินาทีแล้วลองใหม่ 1 ครั้ง ก่อนแสดงว่าเปิดไม่ได้
  (บอตบันทึกแถวหลังส่งการ์ดราว 1 วินาที ผู้ใช้ที่กดปุ่มทันทีจะไม่เจอ 404)

### `services/useMiniSession.ts`

ในโหมดจริง หลัง login โหลดประวัติ และส่งผ่าน Outlet:
`history`, `historyLoading`, `historyError`, `reloadHistory()`, `deleteHistory()`
`miniHref('detail', id)` รับรหัสเคสที่ต้องการเปิด

### `pages/MiniHistory.tsx`

- โหมดจริงใช้ `session.history`; โหมดตัวอย่างใช้ `sampleCases` เหมือนเดิม
- แต่ละรายการลิงก์ไป `miniHref('detail', id)`
- ลบหมายเหตุ "แสดงเฉพาะเคสที่เปิดครั้งนี้… 15 นาที"
- ไม่มีประวัติ: มาสคอต `inspect` + "ยังไม่มีประวัติการตรวจ ส่งข้อความที่สงสัยในแชตเพื่อเริ่มตรวจ"

### `pages/MiniSettings.tsx`

การ์ด "ลบประวัติการตรวจ" (โหมดจริงเท่านั้น) กด 2 ขั้น:
1. "ลบประวัติทั้งหมด"
2. "ลบแล้วกู้คืนไม่ได้" + [ยืนยันลบ] [ยกเลิก]

สำเร็จ: "ลบประวัติแล้ว X รายการ" · ล้มเหลว: ข้อความ error + ลองใหม่ได้

### ข้อความที่ต้องแก้ให้ตรงความจริง

- หน้าบัญชี "ข้อมูลและความเป็นส่วนตัว": เก็บประวัติแชตส่วนตัวไว้ให้ดูย้อนหลัง ลบได้เองในหน้านี้
- FAQ "ทำไมเปิดผลเก่าไม่ได้?": ใช้บัญชี LINE คนละบัญชี หรือลบประวัติไปแล้ว (ตัดเรื่อง 15 นาที)
- `src/mini/README.md`, `LIVE_CASES.md`, `docs/backend/MINI_SETUP.md`: อัปเดตส่วนที่อ้างอายุ 15 นาที

## 5. การทดสอบ

### Backend (Supabase จำลอง)

- `mini_history`: กรองเจ้าของ + `source_type='user'` + 3 สถานะ, เรียงใหม่สุด, จำกัด 50,
  แปลงรหัสถูก, รหัสผิดรูปแบบไม่เรียก Supabase, `delete_all` ลบทุกสถานะของเจ้าของแต่ไม่แตะกลุ่ม,
  exception ของ Supabase กลายเป็น `HistoryUnavailable` โดยไม่มีข้อความดิบ
- `mini_api`: ไม่มี token → 401 ทุก endpoint, เคสคนอื่น → 404 เหมือนเคสไม่มี, Supabase ล่ม → 503,
  ทุกคำตอบมี `no-store`
- `main` + `detection_history`: การ์ดและแถวใช้ `case_id` เดียวกัน, event ซ้ำไม่เกิดแถวซ้ำ,
  รูปภาพบันทึก `"[รูปภาพ] " + OCR`
- เทสต์เดิมทั้งหมด (230) ผ่าน

### Frontend (`tests/mini.test.mjs`)

- `fetchMiniHistory()` ส่ง token ใน header, กรองรายการผิดรูปแบบ
- `fetchMiniCase()` ได้ 404 แล้วลองใหม่ 1 ครั้ง; 404 สองครั้งจึงแสดงว่าเปิดไม่ได้
- หน้าประวัติแสดงหลายเคส ลิงก์ถูกเคส ไม่มีหมายเหตุ 15 นาที
- หน้าบัญชี: ต้องยืนยันก่อนเรียกลบ, ยกเลิกแล้วไม่เรียก API
- build และ lint ผ่าน

### มือถือจริง

1. ส่งข้อความ 2 ข้อความ + รูป 1 รูป → หน้าประวัติเห็น 3 เคส
2. รีสตาร์ตบอต → เคสยังอยู่และเปิดรายละเอียดได้
3. กดลบประวัติ → หน้าประวัติว่าง และเปิดลิงก์เดิมได้ 404
   (ข้อนี้ลบข้อมูลจริงของบัญชีที่ใช้ทดสอบ และทำให้ตัวเลข Dashboard ลดลง ควรใช้บัญชีทดสอบ)

## 6. ความเสี่ยง

| ความเสี่ยง | การรับมือ |
|---|---|
| ผู้ใช้ลบแล้วตัวเลข Dashboard ลด | แจ้งผู้ดูแล Dashboard ก่อน deploy |
| `sub` ของ LINE Login ไม่ตรง `userId` ของบอต | ใช้ Provider เดียวกัน (ยืนยันแล้ว: เปิดเคสจากมือถือได้ 200) |
| Supabase ช้าทำให้หน้าเว็บค้าง | timeout ของ client 10 วินาที (ค่าเดิม) + หน้าเว็บยกเลิกคำขอเมื่อเปลี่ยนหน้า |
| ผู้ใช้กดปุ่มบนการ์ดก่อนบอตบันทึกแถวเสร็จ | หน้าเว็บลองใหม่ 1 ครั้งหลัง 404 (ส่วนที่ 4) ไม่ย้ายการบันทึกไปก่อนส่ง เพราะ `warning_sent` ต้องรู้ผลการส่งก่อน |
| ข้อความเต็มรั่วผ่านรายการ | รายการส่งเฉพาะ `title` 60 ตัวอักษร ข้อความเต็มเฉพาะหน้ารายละเอียดของเจ้าของ |
