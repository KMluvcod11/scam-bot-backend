# ความเสถียรของ LINE Webhook

## การกัน event ซ้ำ

- ใช้ `webhookEventId` ไม่ใช้ข้อความหรือ `isRedelivery` เป็นตัวตัดสิน
- `event_guard.py` ตรวจและจอง ID พร้อมกันด้วย lock ก่อนเริ่มวิเคราะห์
- ID ที่กำลังทำจะไม่ถูกลบทิ้งกลางงาน; ID ที่จบแล้วจำไว้ 24 ชั่วโมง
- เก็บรวมสูงสุด 10,000 ID ถ้าเต็มจะคืน HTTP 503 สำหรับ event ใหม่ ไม่ลบรายการเก่าที่ยังไม่หมดอายุ
- ID ซ้ำตอบรับ HTTP 200 โดยไม่วิเคราะห์หรือส่ง LINE ซ้ำ
- นับว่าเคยพยายามทำแล้วแม้ตรวจหรือส่งไม่สำเร็จ เพื่อคงนโยบายเงียบและไม่ retry อัตโนมัติ
- เก็บเฉพาะในหน่วยความจำของ process เดียว: รีสตาร์ตหรือ `--reload` แล้วข้อมูลหาย
- ต้องรัน worker เดียว การรองรับหลาย worker/หลายเครื่องหรือกันซ้ำข้ามการรีสตาร์ตต้องใช้ที่เก็บร่วมกันเพิ่มเติม
- ไม่ใช่การรับประกัน exactly-once: หาก process ล่มหรือหมดอายุ cache อาจรับ ID เดิมอีกครั้ง

## การตรวจคำขอ

- ตรวจ header ลายเซ็นและ UTF-8 จาก body เดิมก่อนอ่าน JSON
- คำขอไม่ผ่านลายเซ็นหรือโครงสร้างผิดคืน 400 ไม่เรียก AI และไม่เปิดเผย body/token ใน error
- ตรวจ payload ทั้งชุดก่อนเริ่มทำงาน เพื่อไม่ทำ event แรกไปแล้วค่อยพบข้อมูลเสียท้ายชุด
- `events: []` ยังคืน 200 สำหรับการตรวจ Webhook; event ที่ไม่ใช่ข้อความ Text ยังคงข้าม
- Text ต้องมี `webhookEventId`, `replyToken` และข้อมูลที่ LINE SDK อ่านได้

## ความหมายของ log

- `BYPASS` / `PASS`: ข้ามตามกฎ ไม่ใช่การยืนยันว่าปลอดภัย
- `MATCH`: เข้าเกณฑ์เตือนจากคะแนน Vector ไม่ใช่ผลจาก LLM
- `LLM RESULT`: ผลจาก LLM ที่ผ่านการตรวจรูปแบบข้อมูล
- `CHECK ERROR`: ตรวจไม่ได้; `FALLBACK`: ใช้กฎสำรองเพราะ LLM ไม่สำเร็จ
- `DUPLICATE`: event เดิมถูกข้าม; `SKIP`: ประเภท event ไม่รองรับ
- LINE API ยอมรับคำขอส่ง ไม่ได้ยืนยันว่าผู้รับอ่านคำเตือนแล้ว

## ทดสอบในเครื่อง (ไม่เรียกบริการจริง)

จากโฟลเดอร์ราก `linebot` ใน PowerShell:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s scam-bot-backend/tests -p "test_*.py" -v
```

งานนี้ไม่เปลี่ยน Threshold, prompt หรือเพิ่มการตรวจพนัน และยังไม่ได้เพิ่มคิวถาวร/กำหนด timeout ให้ทุกบริการ
# การติดตามงานและ timeout

- ใช้ log รูปแบบเดิม `[NEW MESSAGE]`, `[STAGE]`, `[LLM RESULT]`, `[ACTION]` และเติม `[trace=รหัสสุ่ม 8 หลัก]` เพื่อแยกงาน รวม log ใน thread pool
- ไม่แสดง `[START]` / `[END]` หรือเวลาทุกขั้นตอน; เฉพาะ API ผิดพลาดจึงแสดง `[ERROR]` พร้อม stage, elapsed และชนิด exception
- รหัสสั้นใช้ช่วยอ่าน log เท่านั้น ไม่ใช่ event ID สำหรับกันซ้ำ และไม่รับประกันความไม่ซ้ำตลอดอายุระบบ
- Gemini ตั้ง timeout 20,000 ms และ attempts=1 (ไม่ retry ภายใน SDK); Vector RPC ตั้ง timeout 10 วินาที; LINE คง timeout 10 วินาทีเดิม
- timeout เหล่านี้จำกัดการรอเครือข่ายตาม SDK ไม่ใช่ hard deadline รวมทั้งข้อความ และไม่ได้ฆ่า worker thread
- เมื่อ embedding/Vector ล้มเหลว หรือ LLM เกิด HTTP client timeout จะคืน `status=error, is_scam=None` และไม่ส่งคำเตือน ไม่สรุปว่าปลอดภัย
- กรณี LLM ผิดพลาดชนิดอื่นยังลองโมเดลสำรองและใช้กฎ fallback เดิม
- ทดสอบ offline ด้วย timeout จำลองและข้อความพร้อมกัน; ยังต้องทดสอบ S7 จริงหลัง restart เพื่อระบุสาเหตุเดิม ไม่ได้ยืนยันว่าเครือข่ายจริงหายค้างแล้ว
