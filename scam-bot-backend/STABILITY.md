# ความเสถียรของ LINE Webhook

## บันทึกเมื่อบอตเข้ากลุ่ม

- รับ `join` ที่ source เป็น `group` หลังตรวจลายเซ็น, groupId, event ID และ timestamp; ไม่ใช่ `memberJoined` ของสมาชิกคนอื่น
- ใช้ EventGuard เดิมและทำงานใน thread pool: `save_group_join` บันทึก `line_sources` ก่อน แล้วขอชื่อผ่าน LINE Group Summary API (timeout 10 วินาที)
- เก็บ `bot_joined_at` จากเวลา event เป็นเวลาเข้าร่วมครั้งล่าสุดที่ได้รับ ไม่เดาจากเวลาข้อความแรก และไม่เพิ่ม `detection_logs`/ยอดสแกน
- ดึงชื่อไม่สำเร็จ: เก็บกลุ่มไว้และไม่เขียน null ทับชื่อเดิม; บันทึกฐานล้มเหลว: log `GROUP ERROR` และคืน False แต่ webhook ยังตอบ 200 ตามนโยบายไม่ retry เดิม
- join ซ้ำใช้รหัส event กันซ้ำใน process เดียวตามข้อจำกัดด้านล่าง ไม่มีคิวถาวรหรือ retry งานดึงชื่อ
- กลุ่มที่มีอยู่ก่อนอัปเดตจะไม่ดึงชื่อย้อนหลังเอง; ทดลองกับกลุ่มทดสอบใหม่ หรือเชิญบอตออก/เข้าใหม่ด้วยตนเอง แล้วรีเฟรช Dashboard
- ยังไม่ดึงจำนวนสมาชิกหรือติดตามการเปลี่ยนชื่อ; สถานะขึ้นกับ join/leave ที่ได้รับ ไม่ใช่การสอบถามสมาชิกแบบสด
- ทดสอบ: restart บอต → เชิญเข้ากลุ่มทดสอบ → ต้องเห็น `GROUP JOIN saved=true name_loaded=true` → refresh Dashboard; จำนวนสแกนไม่เพิ่มจาก join
- อ้างอิง: https://developers.line.biz/en/reference/messaging-api/#get-group-summary

## การกัน event ซ้ำ

### เมื่อบอตออกจากกลุ่ม

- รับ `leave` ของ group โดยตรวจลายเซ็น, groupId, event ID และ timestamp เหมือน join; ไม่ต้องมี replyToken และไม่ส่งข้อความตอบ/เรียก AI
- `save_group_leave` update เฉพาะ `is_active=false` ของกลุ่มนั้น ไม่ลบแถว ชื่อ หรือ detection_logs; ไม่เพิ่มยอดสแกน
- Dashboard API กรองเฉพาะกลุ่ม `is_active=true` ในรายการกลุ่มที่เชื่อมต่อ แต่หน้าประวัติยังใช้ข้อมูลเดิมทั้งหมด; ต้องรีเฟรชหน้าเพื่อโหลดใหม่
- เชิญกลับ: join ใช้ `line_source_id` เดิมและตั้ง active ไม่สร้างรายการกลุ่มซ้ำ
- ฐานข้อมูลล้มเหลวหรือไม่พบแถว: คืน False พร้อม log; webhook ยังตอบ 200 ตามนโยบายเดิม ไม่มี retry อัตโนมัติ
- กลุ่มที่ออกก่อนติดตั้งโค้ดนี้จะไม่ถูกแก้ย้อนหลัง ต้องทดสอบเชิญเข้าแล้วออกอีกครั้งหลัง restart ทั้งบอตและ Dashboard API
- ponytail: สถานะใช้ลำดับงานที่เขียนสำเร็จ; ถ้าต้องรองรับ event มาช้า/สลับลำดับข้ามการรีสตาร์ต ให้เพิ่มเวลา lifecycle event และ conditional update ในฐานข้อมูล
- ทดสอบ: join → refresh เห็นกลุ่ม → นำบอตออก → log `GROUP LEAVE saved=true` → refresh กลุ่มหาย แต่ประวัติยังอยู่ → เชิญกลับ กลุ่มเดิมกลับมา
- อ้างอิง leave event: https://developers.line.biz/en/reference/messaging-api/#leave-event

- ใช้ `webhookEventId` ไม่ใช้ข้อความหรือ `isRedelivery` เป็นตัวตัดสิน
- `event_guard.py` ตรวจและจอง ID พร้อมกันด้วย lock ก่อนเริ่มวิเคราะห์
- ID ที่กำลังทำจะไม่ถูกลบทิ้งกลางงาน; ID ที่จบแล้วจำไว้ 24 ชั่วโมง
- เก็บรวมสูงสุด 10,000 ID ถ้าเต็มจะคืน HTTP 503 สำหรับ event ใหม่ ไม่ลบรายการเก่าที่ยังไม่หมดอายุ
- ID ซ้ำตอบรับ HTTP 200 โดยไม่วิเคราะห์หรือส่ง LINE ซ้ำ
- นับว่าเคยพยายามทำแล้วแม้ตรวจหรือส่งไม่สำเร็จ เพื่อคงนโยบายเงียบและไม่ retry อัตโนมัติ
- เก็บเฉพาะในหน่วยความจำของ process เดียว: รีสตาร์ตหรือ `--reload` แล้วข้อมูลหาย
- ต้องรัน worker เดียว การรองรับหลาย worker/หลายเครื่องหรือกันซ้ำข้ามการรีสตาร์ตต้องใช้ที่เก็บร่วมกันเพิ่มเติม
- ไม่ใช่การรับประกัน exactly-once: หาก process ล่มหรือหมดอายุ cache อาจรับ ID เดิมอีกครั้ง

## การตรวจคำขอ

- ตรวจ header ลายเซ็นและ UTF-8 จาก body เดิมก่อนอ่าน JSON
- คำขอไม่ผ่านลายเซ็นหรือโครงสร้างผิดคืน 400 ไม่เรียก AI และไม่เปิดเผย body/token ใน error
- ตรวจ payload ทั้งชุดก่อนเริ่มทำงาน เพื่อไม่ทำ event แรกไปแล้วค่อยพบข้อมูลเสียท้ายชุด
- `events: []` ยังคืน 200 สำหรับการตรวจ Webhook; ส่วนตัวรองรับ postback เรียนรู้และตอบแจ้งเมื่อสื่อไม่รองรับ ส่วน group/room ข้าม event ที่ไม่ใช่ Text
- Text ต้องมี `webhookEventId`, `replyToken` และข้อมูลที่ LINE SDK อ่านได้

## ความหมายของ log

- `BYPASS` / `PASS`: ข้ามตามกฎ ไม่ใช่การยืนยันว่าปลอดภัย
- `MATCH`: เข้าเกณฑ์เตือนจากคะแนน Vector ไม่ใช่ผลจาก LLM
- `LLM RESULT`: ผลจาก LLM ที่ผ่านการตรวจรูปแบบข้อมูล
- `CHECK ERROR`: ตรวจไม่ได้; `FALLBACK`: ใช้กฎสำรองเพราะ LLM ไม่สำเร็จ
- `DUPLICATE`: event เดิมถูกข้าม; `SKIP`: ประเภท event ไม่รองรับ
- LINE API ยอมรับคำขอส่ง ไม่ได้ยืนยันว่าผู้รับอ่านคำเตือนแล้ว

## ข้อความสั้นในกลุ่มและข้อมูลใน log

- ไม่เกิน 25 ตัวอักษรและไม่มีคำบ่งชี้: ข้ามเหมือนเดิม
- ข้อความสั้นที่มีคำบ่งชี้ เช่น OTP/รหัสผ่าน/โอนเงิน: ค้น Vector แล้วใช้ตัวตรวจบริบทแบบส่วนตัว แม้คะแนนต่ำหรือสูงมาก ไม่เตือนจาก keyword หรือคะแนนเพียงอย่างเดียว
- ตัวตรวจนี้วิเคราะห์ข้อความที่ส่งมา ไม่ได้อ่านบทสนทนาย้อนหลัง; ถ้าผลไม่ใช่ scam กลุ่มยังเงียบ ถ้าบริการพังคืน error ไม่ใช้คะแนนสำรองเตือน
- ใช้ API เพิ่มในข้อความสั้นกลุ่มนี้ จึงต้องลองทั้งคำขอรหัสและข้อความเตือนว่าอย่าให้รหัส
- log เก็บจำนวนตัวอักษรแทนข้อความ และไม่พิมพ์ข้อความตัวอย่าง/เหตุผลจาก LLM; history ในฐานข้อมูลยังเก็บเหมือนเดิม ไม่ได้ลบข้อมูลเก่าหรือปิด log ของระบบภายนอก
# การติดตามงานและ timeout

## แชทส่วนตัว — ขั้นแรกสำหรับเดโม 22 กันยายน 2569

- แยก `source.type=user` ออกจาก group/room; ข้อความยาวในกลุ่มยังใช้เกณฑ์เดิม ข้อความสั้นมีคำบ่งชี้ใช้ข้อยกเว้นด้านบน
- คำทักทาย/ขอบคุณที่ตรงรายการตอบสำเร็จรูป ไม่เรียก AI; ข้อความอื่นค้น Vector แล้วเรียก LLM แม้สั้นหรือคะแนนต่ำ (ใช้ API มากกว่าเส้นทางกลุ่ม)
- ผลส่วนตัวมี conversation, no_risk_found, risk_found, uncertain และ error; ไม่ใช้ False จากกฎข้ามหรือ fallback เป็นผลรับรองว่าปลอดภัย
- ส่วนตัวที่ LLM ล้มเหลวไม่ใช้คะแนน Vector สำรองมาตอบแทน; error แจ้งให้ผู้ใช้ส่งมาตรวจใหม่ ไม่ retry ส่งคำตอบอัตโนมัติ
- รูปภาพและสื่ออื่นในส่วนตัวตอบว่ายังไม่รองรับ; ในกลุ่มยังข้ามเช่นเดิม
- ข้อความกำกวมให้ส่งข้อความเดิมรวมบริบทใหม่ในข้อความเดียว ยังไม่มีความจำบทสนทนา
- ยังไม่เปิดตรวจเว็บปลายทางหรือเพิ่มปุ่มลองใหม่; ปุ่มเรียนรู้และเคสชั่วคราวดูหัวข้อถัดไป ไม่แก้ฐานข้อมูลหรือ Dashboard
- ทดสอบ offline เป็น regression ไม่ยืนยันความแม่นยำของ Gemini จริง และยังต้องทดสอบ LINE จริงก่อนนำเสนอ

### ทดลองจริงทีละข้อความหลัง restart

1. ส่วนตัว: `สวัสดีครับ` → แนะนำหน้าที่; `ขอบคุณ` → ตอบสั้น
2. ส่วนตัว: `ส่ง OTP มา` → ต้องไม่ข้ามเพราะข้อความสั้น; ตรวจ log ว่าเข้า LLM
3. ส่วนตัว: ข้อความหลอกลงทุน S5 / แอบอ้างตำรวจ S7 → คาดหวังคำเตือนจากการประเมิน
4. ส่วนตัว: ข้อความยกตัวอย่าง Scam เพื่อเตือนภัย → ตรวจว่า AI ไม่เหมารวมเป็นคำชักชวน
5. ส่วนตัว: URL อย่างเดียว → ควรระบุข้อมูลไม่พอ ไม่อ้างว่าเปิดตรวจเว็บไซต์แล้ว
6. ส่วนตัว: ภาพหรือสติกเกอร์ → แจ้งยังไม่รองรับ
7. กลุ่ม: คำทักทายยังเงียบ และข้อความ Scam ยังเตือนตามเดิม

- ใช้ log รูปแบบเดิม `[NEW MESSAGE]`, `[STAGE]`, `[LLM RESULT]`, `[ACTION]` และเติม `[trace=รหัสสุ่ม 8 หลัก]` เพื่อแยกงาน รวม log ใน thread pool
- แสดง `[TIME]` ของ embedding, vector_db, llm, line_reply, history และ event_total; ข้อผิดพลาดแสดงชนิด exception โดยไม่พิมพ์รายละเอียดข้อความ
- รหัสสั้นใช้ช่วยอ่าน log เท่านั้น ไม่ใช่ event ID สำหรับกันซ้ำ และไม่รับประกันความไม่ซ้ำตลอดอายุระบบ
- Gemini ตั้ง timeout 20,000 ms และ attempts=1 (ไม่ retry ภายใน SDK); Vector RPC ตั้ง timeout 10 วินาที; LINE คง timeout 10 วินาทีเดิม
- timeout เหล่านี้จำกัดการรอเครือข่ายตาม SDK ไม่ใช่ hard deadline รวมทั้งข้อความ และไม่ได้ฆ่า worker thread
- เมื่อ embedding/Vector ล้มเหลว หรือ LLM เกิด HTTP client timeout จะคืน `status=error, is_scam=None` และไม่ส่งคำเตือน ไม่สรุปว่าปลอดภัย
- กรณี LLM ผิดพลาดชนิดอื่นยังลองโมเดลสำรอง; fallback ตามคะแนนใช้เฉพาะเส้นทางกลุ่มข้อความยาว ไม่ใช้กับส่วนตัวหรือข้อความสั้นมีคำบ่งชี้
- ทดสอบ offline ด้วย timeout จำลองและข้อความพร้อมกัน; ยังต้องทดสอบ S7 จริงหลัง restart เพื่อระบุสาเหตุเดิม ไม่ได้ยืนยันว่าเครือข่ายจริงหายค้างแล้ว
