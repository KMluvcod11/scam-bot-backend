# สรุปงาน Backend และข้อมูลสำหรับ Scam Detection Bot

วันที่: 30 กันยายน 2569

ผู้รับผิดชอบ: หยก
สถานะ: เตรียมตารางและเชื่อมการบันทึกผลตรวจแล้ว ทดสอบกับ Supabase จริงด้วยข้อมูลจำลองสำเร็จ

## 1. ขอบเขตงานที่ทำในครั้งนี้

เตรียมระบบรับผลวิเคราะห์ของบอตและบันทึกประวัติใน Supabase เพื่อให้สามารถนำข้อมูลไปแสดงบน Dashboard ในขั้นต่อไป โดยแยกประวัติผลตรวจออกจาก `scam_dataset` ซึ่งเป็นชุดข้อมูลตัวอย่างสำหรับค้นหาเทียบเคียง

ขอบเขตปัจจุบันมุ่งที่การตรวจข้อความธรรมดา ยังไม่พัฒนา LINE Mini App หรือฟีเจอร์ตรวจเว็บไซต์จากลิงก์ การเปลี่ยนแปลงครั้งนี้ไม่ได้เพิ่มตัวตรวจเว็บไซต์ปลายทาง

## 2. สิ่งที่ดำเนินการแล้ว

### 2.1 ออกแบบและเตรียมฐานข้อมูล

จัดทำ SQL และผู้ใช้นำไปรันใน Supabase แล้ว โดยมีองค์ประกอบดังนี้:

| ตารางหรือ View | หน้าที่ |
| --- | --- |
| `line_sources` | เก็บต้นทางข้อความ เช่น กลุ่ม LINE, room และแชตส่วนตัว พร้อมเวลาที่พบล่าสุด |
| `detection_logs` | เก็บข้อความ เวลา ผลตรวจ ระดับความเสี่ยง เหตุผล และสถานะการตอบกลับ LINE |
| `dashboard_admins` | ระบุบัญชี Supabase Auth ที่ได้รับสิทธิ์อ่านข้อมูลใน Dashboard |
| `dashboard_daily_stats` | รวมจำนวนข้อความ ผลที่พบความเสี่ยง การตรวจที่ผิดพลาด และการตอบกลับรายวัน |

กำหนด `line_event_id` เป็นค่าที่ห้ามซ้ำ และเพิ่มดัชนีสำหรับค้นหาประวัติตามเวลา ต้นทาง และระดับความเสี่ยง

SQL มีการเปิด Row Level Security เพื่อจำกัดการอ่านตารางให้บัญชีที่อยู่ใน `dashboard_admins` ส่วน Backend ใช้คีย์สำหรับเขียนข้อมูลที่เก็บไว้ใน `.env`

มีการแก้ SQL เพิ่ม `security_invoker` ให้ View ใช้สิทธิ์ของผู้เรียก ผู้ใช้ควรรันไฟล์ SQL ฉบับล่าสุดอีกครั้งเพื่อให้การแก้ส่วนนี้มีผล ยังไม่ได้ยืนยันการตั้งค่า View บนฐานข้อมูลจริง

### 2.2 กำหนดรูปแบบข้อมูลสำหรับทีม

จัดทำ `DATA_CONTRACT.md` อธิบายชื่อฟิลด์ ชนิดผลตรวจ และความหมายของข้อมูล เพื่อให้ขุนและนนท์ใช้เป็นเอกสารอ้างอิงร่วมกัน เอกสารนี้ยังต้องให้ทีมตรวจและตกลงรายละเอียดร่วมกัน

ผลตรวจรองรับสถานะ `bypassed`, `conversation`, `no_risk_found`, `risk_found`, `uncertain` และ `error` โดยการตรวจไม่สำเร็จเก็บ `is_scam = null`

### 2.3 เชื่อมการบันทึกผลตรวจกับ Backend

เพิ่มโมดูล `detection_history.py` และเรียกใช้งานจาก `main.py` สำหรับข้อความประเภท text ในกลุ่มและแชตส่วนตัว รวมถึงกรณีตรวจไม่สำเร็จ

บันทึกต้นทางลง `line_sources` และผลตรวจลง `detection_logs` โดยใช้ `webhookEventId` ของ LINE เป็น `line_event_id` การเขียนซ้ำใช้คำสั่งที่ข้ามแถวเดิมเมื่อรหัสตรงกัน จึงไม่เพิ่มประวัติซ้ำหรือเขียนทับผลเดิม

หากฐานข้อมูลเชื่อมต่อหรือบันทึกไม่ได้ ระบบรายงานชนิดข้อผิดพลาดโดยไม่แสดงคีย์หรือข้อความ error ดิบ และการทำงานของบอตสามารถดำเนินต่อได้ อย่างไรก็ตาม ยังไม่มีระบบเก็บงานค้างเพื่อส่งข้อมูลที่บันทึกล้มเหลวกลับไปใหม่

### 2.4 เตรียมค่าการเชื่อมต่อ

เพิ่มตัวแปร `SUPABASE_HISTORY_KEY` สำหรับการเขียนประวัติ และสร้าง `.env` สำหรับเก็บค่าจริงในเครื่อง ผู้ใช้ใส่ Project URL และคีย์แล้ว รายงานฉบับนี้ไม่แสดงค่าคีย์

### 2.5 เพิ่มเครื่องมือและการทดสอบ

เพิ่ม `test_supabase_history.py` สำหรับทดสอบการบันทึกโดยใช้ผลวิเคราะห์จำลอง จึงทดสอบส่วนฐานข้อมูลได้ก่อนมีคีย์ LINE และ Gemini

เพิ่มชุดทดสอบโมดูลประวัติ และปรับตัวจำลองในชุดทดสอบ Webhook ให้รองรับโมดูลใหม่

## 5. ข้อจำกัดและงานที่ยังเหลือ

- ยังไม่ได้ทดสอบข้อความจริงจาก LINE และการวิเคราะห์ด้วย Gemini ร่วมกับการบันทึกประวัติ
- ยังไม่ได้ทำ API สำหรับสถิติ ประวัติที่ค้นหา/กรอง/แบ่งหน้าได้ และรายละเอียดผลตรวจรายรายการ
- ยังไม่ได้เชื่อม Dashboard หรือทดสอบสิทธิ์ผู้ดูแลร่วมกับหน้าจอจริง
- คะแนนความคล้ายและข้อมูลการจับคู่ยังไม่ได้ถูกส่งออกจากผลวิเคราะห์เข้าสู่ประวัติ จึงยังเป็น `null` ได้ วิธีตัดสินส่วนใหญ่ยังเป็น `unknown`
- ยังไม่ได้เพิ่มประเภทภัยสำหรับกราฟแยกประเภทการหลอกลวง
- ชื่อกลุ่มและจำนวนสมาชิกยังไม่ได้ดึงจาก LINE API
- ยังไม่ได้เพิ่มการปกปิดข้อมูลส่วนตัวในข้อความที่จัดเก็บ ข้อมูลข้อความฉบับเต็มจึงต้องอยู่ภายใต้สิทธิ์ผู้ดูแล
- ต้องตรวจว่าคีย์จริงไม่อยู่ใน `.env.example` ก่อนนำโค้ดขึ้น Git เนื่องจากก่อนหน้านี้ผู้ใช้เคยวางคีย์ในไฟล์ตัวอย่าง และควรเปลี่ยนคีย์ที่ปรากฏในภาพหน้าจอ
- ยังไม่ได้ commit, push หรือ deploy โค้ดที่แก้ไขในครั้งนี้

## 6. ขั้นตอนถัดไปเมื่อกลับมาทำต่อ

1. ให้ทีมตรวจรูปแบบข้อมูลใน `DATA_CONTRACT.md` และยืนยันฟิลด์ที่ Dashboard ต้องใช้
2. ให้ขุนติดตั้งแพ็กเกจและนำโค้ดล่าสุดไปรันกับการตั้งค่า LINE/Gemini ที่ใช้งานจริง
3. ส่งข้อความธรรมดาผ่าน LINE และตรวจว่ามีผลตรวจตรงกันใน `detection_logs`
4. เมื่อตรวจเส้นทางจริงผ่านแล้ว จึงทำ API และเชื่อม Dashboard ของนนท์

พักงานไว้ที่ขั้นทดสอบการบันทึกผลจำลองกับฐานข้อมูลจริงสำเร็จตามคำขอของผู้ใช้
